# 外部量化策略接入与固定数量轮动模板

更新：2026-10-12。本文依据当前仓库源码，适用于外部 Python 程序通过大 QMT 桥接普通股票、ETF 的只做多策略。

推荐结构是：**策略输出目标组合，组合管理程序安排调仓，现有桥接层负责调用大 QMT。** 因子计算和组合管理放在外部 Python 环境，QMT 内部保留行情与交易接口。这样可以隔离 QMT 内置 Python 的依赖限制，并让回测、离线演练和实盘复用同一套选股与调仓计算。

参考文件：

- [可离线运行的调仓模板](../examples/external_rotation_template.py)：标准库实现，不连接 QMT，不发送或撤销委托。
- [模板验证](../tests/bigqmt_signal_trader/test_external_rotation_template.py)：验证资金、名额、委托状态、可卖数量和数据时效等约束。
- [部署说明](DEPLOY_QUICKSTART.md)、[使用指南](USER_GUIDE.md)：现有桥接服务的配置与部署。

模板实现了“如何算下一批订单”，还没有实现真实下单循环、长期保存的订单记录、进程锁、自动撤单与重启恢复。下面给出了这些部分的接口、状态规则和接入顺序；不能只把模板的输出接到 `order_stock()` 就当成完整实盘程序。

## 1. 项目现有能力与正确接入位置

| 功能 | 当前代码 | 接入时的用法与边界 |
|---|---|---|
| 外部行情和交易接口 | `src/bigqmt_signal_trader/xtquant_compat.py` | 推荐显式导入，沿用 `XtQuantTrader`、`StockAccount`、`xtdata`；旧策略也可以通过 `src/xtquant/` 替换原 import |
| 资产与持仓 | `query_stock_asset()`、`query_stock_positions()` | 使用真实账号的可用资金、总持仓、可卖数量；查询错误必须停止产生新订单 |
| 委托与成交 | `query_stock_orders()`、`query_stock_trades()`、`query_execution_snapshot()` | 查询全部账户记录做风险检查，再按本地订单记录归属策略；注意后者默认会过滤委托策略名 |
| 委托/成交/错误回报 | `XtQuantTraderCallback`、`exec_events.py` | 已有事件通道，不是只有查询；回报用于及时更新，定期查询用于补齐遗漏 |
| 下单与撤单 | `order_stock_result()`、`order_stock()`、`cancel_order_stock_sysid()` | 推荐组合管理程序统一调用；提交、成交、撤单完成是不同状态 |
| 短期重复请求保护 | `redis_rpc.py` 中按 `request_id` 去重 | 当前内存记录有数量和时间限制，服务重启会丢失；不能替代长期保存的业务订单记录 |
| 简单买卖信号队列 | `adapters/signal_redis.py`、`adapters/state_redis.py` | 可以传递单笔买卖信号；不能直接发送目标组合 JSON 给 `TradeSignal` |
| 现有信号执行应用 | `app.py`、`risk_guard.py` | 风控主要检查过期、买卖数量、可卖数量；没有完整组合预算、固定名额、资金预留和订单生命周期管理 |
| 外部回测 | `src/bigqmt_backtest/strategy.py`、[ZMQ 回测说明](ZMQ_BACKTEST_BRIDGE.md) | 已有外部策略回测入口；需要自行适配目标组合规划器并核对撮合、费用与交易规则 |

为什么把组合管理加在外部应用层：传输层负责把一次调用送到 QMT，交易适配层负责字段转换，组合管理负责多个标的之间的资金、名额、先后顺序。固定数量轮动的约束属于组合管理。不要在 Redis/ZMQ 收发代码中塞选股和组合预算，也不要在每个因子脚本里复制风控和重试逻辑。

如果以后需要所有 RPC 调用者都受同一套账户风控约束，应在**共同的服务端订单入口**增加账户风险检查。外部程序自己的风控管不到其他程序直接调用 RPC 的订单；当前 `rpc_allow_order_methods` 只是下单权限开关。

部分早期说明仍写着“回调暂未推送”或“适配器后续实现”，与当前源码不同。本文以当前实现及对应测试为准。

## 2. 整体流程与模块分工

```text
外部行情 / 因子 / 其他策略的信号
            ↓
数据检查：完整性、时间范围、复权、可用日期
            ↓
策略：候选评分、排序 → 带版本和有效期的目标组合
            ↓
账户协调器：接收目标、账户锁、风险覆盖、对账
            ↓
组合规划器：目标与实际持仓比较 → 下一批买卖计划
            ↓
订单管理：先记录订单与资源预留 → 调用现有 RPC → 跟踪回报
            ↓
大 QMT / 券商
            ↓
成交、委托、持仓、资金回到协调器 → 核对后再规划下一批
```

建议外部策略项目按职责组织；以下是建议目录，不是本仓库已实现的模块：

```text
rotation_app/
  config.py               # 账户、预算、名额、时段、风险上限
  market_data.py          # 行情读取、历史数据、数据质量检查
  strategy.py             # calculate_scores() / produce_target()
  portfolio.py            # 调仓计算，可复用本仓库示例
  risk.py                 # 账户风险、单标的风险、冷却名单
  broker.py               # 对接 xtquant_compat，转换真实接口结果
  orders.py               # 委托状态、撤单、未知结果处理
  records.py              # SQLite 或服务数据库，保存目标、订单、成交
  coordinator.py          # 单账户唯一的执行循环
  monitor.py              # 状态、异常、告警与停止开关
```

单账户低频轮动通常一个执行进程即可，数据准备可以单独运行。研究计算不应占用订单回报处理线程。Redis/ZMQ/Pipe 的选择影响部署方式，不改变组合管理规则；不要从旧延迟文档推导当前环境性能，实际延迟应在自己的运行环境测量。

## 3. 策略输出目标组合，不直接决定每一笔买卖

普通轮动信号表达的是“这一轮想持有谁”，不是“无条件再买多少股”。建议完整目标一次性发布，避免五个标的分五条消息到达时被当成五次独立组合更新。

外部目标消息可采用以下结构，接收层需要自行实现校验与转换；它不是现有 `TradeSignal` 消息格式：

```json
{
  "schema_version": 1,
  "account_id": "YOUR_ACCOUNT_ID",
  "strategy_id": "rotation_v1",
  "version": 1,
  "created_at": "2026-10-12T09:35:00+08:00",
  "data_cutoff": "2026-10-09T15:00:00+08:00",
  "expires_at": "2026-10-12T10:30:00+08:00",
  "symbols": ["SYMBOL_1", "SYMBOL_2", "SYMBOL_3", "SYMBOL_4", "SYMBOL_5"]
}
```

- `version` 按账户、策略递增，并在数据库中保存；不要每天从 1 开始。延迟到达的旧版本不得重新成为当前目标。
- 相同版本、相同内容是重复投递；相同版本、不同内容应拒收并记录异常。可以对规范化后的消息保存内容摘要。
- `data_cutoff` 说明策略实际用了何时之前的数据。接收时间不是行情时间，也不是财务数据可知时间。
- 有效期到达后停止按旧目标产生新订单，继续跟踪已发订单。是否撤销剩余买单由订单策略决定，不假设过期自动撤单。
- 空消息、选股失败和明确清仓分开处理。模板默认拒绝空目标；只有开启明确清仓规则才允许空组合。
- 新目标替换旧目标时，先保存新版本并使旧计划失效，再处理旧委托；已成交部分成为实际持仓，不能回滚。旧委托未结束前暂停新一轮交易。

选股流程建议为：验证数据 → 明确候选范围 → 排除不符合交易/流动性要求及处于冷却期的标的 → 评分 → 排名缓冲 → 选出最多 N 个标的。

减少来回换仓可以使用排名缓冲，例如 N=5，已有持仓仍在前 8 名就优先保留，空位再用排名靠前的候选补齐。N 和缓冲大小属于策略参数，需要回测验证。模板的 `select_targets()` 演示了该做法，评分本身留给外部策略实现。

权重默认按 N 等额分配。候选不足、资金不足、交易受限时允许留现金，不把资金自动集中到剩余少数标的。若要输出自定义权重，需要扩展模板的目标模型，并同时校验权重合计、单标的上限和总体仓位。

## 4. 固定数量的含义要提前确定

建议把“目标 N 只”和“实际最多 N 只”分开定义：通常希望完成调仓后持有 N 只，同时执行途中也不得超过 N 只。市场限制下可能暂时不足 N 只；必须接受这种情况。

如果旧标的卖不掉，要求“任何时候最多 N 只”“马上换成新组合”“任何时候必须正好 N 只”可能相互冲突。模板采用严格名额规则：旧持仓没有归零就保留其名额，允许暂时少持有或保留现金。

**名额计数 = 实际数量大于 0 的标的 ∪ 有未结束买单的标的 ∪ 结果未知但可能已买入的标的。** 对同一代码取并集，避免重复计数。卖单未成交、撤单处理中、剩余零股都不能释放名额。

例：原持仓 A/B/C/D/E，目标 B/C/D/E/F。先清理 A，核对 A 的持仓为 0，再安排 F。如果 A 停牌或没有可卖数量，继续占一个名额；F 等待，其他保留标的可在预算和风险允许时调整。

模板更保守：账户存在任何未结束委托或结果未知的指令，就等待整批委托结束和对账，再生成下一批。这样容易验证，也避免在持仓更新稍慢时重复补单。需要更高并行度时，再实现“预计完成后的持仓”，不要直接删除这个等待条件。

## 5. 预算、数量与先卖后买

设策略权益为 E、投入比例为 r、最多标的数量为 N：

```text
组合市值上限 = E × r
退出标的暂时卖不掉的市值 = L
单个目标预算 = min(max(0, E × r - L) / N, E × 单标的权重上限)
现金预留 = E × (1 - r)
本批可花资金 = max(0, 券商报告的可用资金 - 现金预留)
```

这里 E 必须有明确归属。专用账户可使用账户权益；共享账户必须使用分配给该策略的资金和市值，不能让每个策略都按账户总资产满额投资。

规划顺序：

1. 对账，并确认当前目标仍有效、账户与行情可用。
2. 清理退出组合的标的，只卖券商报告的可卖数量。
3. 等卖单全部到结束状态，核对成交、持仓和资金。
4. 计算卖不掉的持仓占用，必要时降低保留标的的仓位。
5. 再次对账，用实际可用资金安排买入，预留费用和现金。
6. 跟踪买单，核对结果，未达到目标的部分记录为缺口；只有确认原委托结束才允许产生下一笔补单。

数量计算注意：

- 下单、估值使用未复权的实际价格；因子可以使用明确口径的复权价格，两者不要混用。
- 买入价格、数量按对应品种的最小变价单位、最小买入数量与增加步长计算。
- 卖出上限使用 `can_use_volume`，不是 `volume`。模板将其转换为 `Position.available`。字段定义见[迅投交易文档](https://dict.thinktrader.net/nativeApi/xttrader.html)。
- 同样是股票，不同板块的最小数量规则也可能不同；ETF、转债、期货更不能一律套 100 股。模板要求每只标的显式提供 `InstrumentRule`。
- 允许整笔清理剩余零股时，必须确认该品种和券商支持。部分减仓仍按相应规则处理。
- `cash` 是可用资金时，已扣除了券商冻结的资金；不要再次扣同一笔冻结资金。本地已记录但尚未反映到券商数据的指令，需要额外预留。
- 预计卖出金额不能提前算成可花现金。总资产也不能代替可用资金。
- 用金额偏离容忍范围减少小额反复调仓。手续费最低收费、税费、买卖价差和滑点都应计入。

模板的费用参数是保守的演示预留值，需要按账户实际费率校准；不是对真实费用的预测。多笔限价单每一笔都需要检查单笔金额上限和费用。

## 6. 风控分三处实现

| 层次 | 必要检查 | 失败时的动作 |
|---|---|---|
| 接收目标时 | 账户、策略、版本、有效期、标的重复、候选范围、目标数量、数据是否完整 | 拒收异常目标，保留记录；不能将异常空结果解释为清仓 |
| 每次下单前 | 交易日与时段、账户状态、价格时效、停牌、价格范围、数量规则、单笔金额、单标的上限、总仓位、名额、资金/证券预留 | 拒绝或缩小订单，记录原因；买单暂停不得被普通信号绕过 |
| 持仓期间 | 净值回撤、日内亏损、集中度、流动性、连续拒单、未知委托、连接或数据异常 | 停止加仓、降低仓位或进入人工处理；持续管理已经发出的委托 |

风险参数应该来自策略与账户的验证结果，不能把示例的 95% 投入、费用预留或任何止损阈值当成通用收益最佳值。

止损要作为**有效目标的风险覆盖**处理：把该标的目标降为 0，同时进入冷却名单；策略排名仍选中它时，也不能立即买回。恢复需要满足明确条件或到期。区分“仅停止新买”“允许减仓”“请求撤销未完成买单”“人工确认后恢复”等状态。

保存原始策略目标，同时单独记录风险覆盖版本。实际执行目标由“策略版本 + 风险版本”确定，订单也关联这两个版本。每次发送前复查它们，避免止损已触发，但前一批尚未发送的买单仍按旧目标继续执行。

停牌、没有可卖数量或价格限制时，减仓要求也可能无法马上完成。记录未完成的风险处理，停止扩大相关风险，不把“已发卖单”当成风险已解除。

价格精度、当日价格范围与交易状态需要合约资料。迅投公开文档列出了 `PriceTick`、`UpStopPrice`、`DownStopPrice` 等字段，见[行情文档](https://dict.thinktrader.net/nativeApi/xtdata.html)。实际环境中字段缺失、无效或不适用于该品种时，先验证并采用对应品种规则，不能填一个猜测值继续下单。

## 7. 订单管理：记录在前，网络调用在后

每笔业务订单至少保存这些信息：

```text
account_id, strategy_id, trading_date, target_version, plan_id
client_order_id, rpc_request_id（如果下单封装能提供）
symbol, side, quantity, limit_price, price_type, attempt
reserved_cash / reserved_quantity / reserved_slot
order_sysid（原始字符串）, order_id（兼容接口编号）
state, filled_quantity, created_at, updated_at, error, immutable_payload_hash
```

推荐订单状态：

```text
PREPARED（已记录、已预留）
    → SENDING（即将调用网络）
    → ACKNOWLEDGED / WORKING（已接受或已报）
    → PART_FILLED（部分成交）
    → FILLED / CANCELED / PART_CANCELED / REJECTED（结束）

SENDING / 撤单处理中发生超时或进程崩溃
    → UNKNOWN（实际结果不清楚）→ 对账确认 → 已知状态或人工处理
```

必须遵守：

- 在同一个数据库事务中保存业务订单、不可变参数和资金/证券/名额预留，再把状态改为 `SENDING` 后调用交易接口。
- 数据库提交与券商接单无法组成一个共同事务。程序可能在券商接单后、保存响应前崩溃，所以恢复时 `SENDING` 也要按结果未知处理。
- 同一业务订单只创建一次，使用唯一约束。相同 `client_order_id` 不能对应不同价格或数量。
- 同一目标版本可能经过多批成交逐步完成，不能只用“目标版本 + 标的”作为业务订单身份。每批计划在账户锁内保存独立的回合编号和内容，子订单关联该回合；重复调度同一回合不会生成新订单，上一回合核对完成后才能创建下一回合。
- 备注使用紧凑且唯一的 ASCII 标识，例如 23 字符的 `rot` 加 20 位摘要，并在本地保存完整信息及碰撞检查；不要把长 JSON 塞到委托备注。具体长度需要核对券商限制。
- 保存原始 `order_sysid` 字符串，不能只保存转换后的整数编号。该项目的订单编号可能同时携带两种身份；转成普通整数后，一些恢复撤单场景会丢失原始身份。
- 下单返回编号或异步 `seq` 表示提交阶段的结果，不能把本地持仓立即增加为已成交。成交和券商持仓才是实际数量来源。
- 当前兼容层在下单超时后会查询请求结果；仍无法确认时，业务层进入 `UNKNOWN`，查询委托、成交和持仓后再判断。不要用通用网络重试把下单函数重新调用一遍。
- 当前桥接层按同一 `request_id` 做短期内存去重，源码配置为最多 512 条、有效期 600 秒。新一次 `order_stock_result()` 调用会产生新的请求编号。复用备注也不是跨重启的唯一成交保证。
- “暂时查不到订单”不足以证明未下单。只有明确的未派发/拒绝证据，或经过确认的对账结果，才可释放未知指令的预留；确认不了就停止新增订单并提示处理。

订单状态数字以当前 `xtconstant` 和实际回报为准。本项目普通股票路径中，53/54/56/57 分别对应部分撤销、已撤、全成、废单等结束状态。51/52 仍处于撤单处理中，不能因为发出了撤单请求就释放资源；未知状态同样不能当成结束。

撤单后要处理“撤单与成交同时发生”的情况：等待结束状态，核对最终成交量，再以剩余目标差额创建新子订单。限定改价次数、累计等待时间和价格偏离；达到上限后停止追单，留下明确的目标缺口。

## 8. 回报、对账与重启恢复

回调里只做快速记录或放入本地队列，交给账户协调器统一更新状态。避免在回调线程内运行因子计算、阻塞查询或直接产生下一笔订单。

回报可能重复、顺序不同或断线时遗漏。成交按账户、市场、交易日和成交编号建立唯一约束；字段不足时需要可靠补充身份或进入异常处理，不能猜测去重。**成交记录加数量、委托的累计成交量再加一次，会重复计算；** 两者应核对，而不是相加。

定期以及断线恢复、启动时，读取资产、持仓、全部委托和全部成交，对照本地记录：

1. 找出本地未结束和 `UNKNOWN` 指令，按原始合同号或唯一备注关联真实委托。
2. 补齐遗漏成交，核对最终数量与金额。
3. 查找账户里不属于当前程序的手工/其他策略订单。
4. 对账通过后重建资金、证券和名额预留。
5. 再使用当前有效目标规划下一批；不要原样重发数据库中的旧买卖清单。

`query_execution_snapshot()` 只把委托和成交合并成一次 RPC，**没有把资产和持仓变成共同的原子快照**。几次查询之间也可能发生成交；短时间内的持仓延迟不能当成新的补单依据。可采用有界重复读取、成交记录交叉核对及本地期望数量检查，未能确认一致就等待；终端的数据源时间不明确时，不能仅凭 RPC 刚返回就设置 `reconciled=True`。

模板中的 `AccountView.observed_at` 应是经过校验的账户观察时间，`Quote.observed_at` 应来自行情源。`reconciled` 和 `trading_open` 默认关闭，必须由协调器完成上述检查后开启。

本地单机可使用 SQLite 保存记录和唯一约束，并配合操作系统进程锁。多机执行应使用共享数据库的账户锁、租约和递增执行令牌，让旧实例失去权限后无法继续下单。只有在共同的订单入口也校验执行令牌，才能完整阻止旧实例；仅靠一个会过期的 Redis 锁不够。

## 9. 真实接口接入参考

先完成只读验证。下面脚本只查询，不下单；需要已有服务端配置和运行中的桥接服务：

```python
from bigqmt_signal_trader.xtquant_compat import XtQuantTrader, StockAccount

trader = XtQuantTrader("", 2026101201, account_id="YOUR_ACCOUNT_ID")
account = StockAccount(trader.client.account_id, "STOCK")
try:
    trader.connect()
    trader.subscribe(account)
    asset = trader.query_stock_asset(account)
    positions = trader.query_stock_positions(account)
    execution = trader.query_execution_snapshot(
        account, order_strategy_name="", trade_strategy_name=""
    )  # 显式取消默认策略名过滤，观察账户全部记录。
    if asset.cash is None or asset.total_asset is None:
        raise RuntimeError("账户资金字段不完整，不能据此安排交易")
    print("可用资金:", asset.cash, "账户总资产:", asset.total_asset)
    print("持仓数量:", len(positions))
    print("委托:", len(execution["orders"]), "成交:", len(execution["trades"]))
finally:
    trader.stop()
```

`connect()` 成功主要证明桥接服务可达；账户是否登录、数据是否完整和交易权限是否可用，还需核对真实账户状态与返回数据。不要把一次连接回报当成全部交易条件通过。

外部策略环境与 QMT 内置 Python 分开管理。已有真实 `xtquant` 的环境应先隔离环境或采用合适的源码安装方式，避免两个同名包互相覆盖；见[使用指南中的兼容方式](USER_GUIDE.md)。不要为共享依赖问题在每个策略脚本里打补丁。

账户协调器的实现顺序可以参考以下伪代码。`records`、`risk`、`broker` 是你需要实现的外部模块，下面不是可直接运行的实盘循环：

```python
with records.exclusive_account(account_id):
    # 先保存回报和补查数据，恢复可能已下单但本地没保存响应的情况。
    events = broker.drain_events()
    records.apply_events_once(events)
    view = broker.reconcile(records)

    # 当前目标版本来自数据库；止损等风险覆盖不能被策略重新选中绕过。
    target = risk.apply_to_target(records.latest_valid_target(), view)
    plan = build_plan(target, view, quotes, instrument_rules, settings, now)
    records.save_plan_and_reasons(plan)

    for intent in plan.orders:
        # 账户锁 + 唯一约束 + 同事务资源预留。
        child = records.prepare_once_and_reserve(target.version, plan, intent)
        if child is None:
            continue
        # 每笔发送前复查时间、当前目标、锁、风险和累计资源预留。
        risk.check_before_send(child, broker, records)
        records.mark_sending(child)
        try:
            result = broker.submit(child)  # 内部调用 order_stock_result()
        except Exception as exc:
            # 是否为明确拒绝由 broker 分类；不明确的任何异常都可能已下单。
            records.record_submission_outcome(child, exc)
            break
        records.save_submission_result(child, result)
        # 不在这里假装成交；等回报及对账后再规划下一批。
```

下单封装用 `strategy_name` 保存策略身份、`order_remark` 保存短业务订单编号，并保持限价、数量和方向的实际接口语义。账户风险检查需要覆盖已发订单和本批尚未发出的预留；一批计划中途失败后，不应继续发送依赖失败订单的后续买单。

服务端远程下单仍由私有配置中的 `rpc_allow_order_methods` 控制；保留关闭直到真实执行模块验证完成。模板中的配置参数不是这个权限开关。

如果必须复用 Redis 信号流：先在外部组合管理中把目标拆成受控子订单，再发布符合 `TradeSignal` 格式的买卖信号，并扩展执行端的账户预算、状态与对账。当前 `TradeSignal.amount` 表示数量；它的 `percentage` 用于卖出现有可用数量的比例，不是组合目标权重。当前应用收到信号后标记提交并 ACK，不会自动等成交来完成整轮调仓，也没有完整的崩溃后信号接管流程。不要让信号流消费者和 RPC 协调器同时管理同一笔订单。

## 10. 多策略、账户归属与手工交易

起步优先使用专用账户或清晰隔离的资金分配，降低对账复杂度。

同一账户运行多个策略时，需要一个共同的账户执行入口：各策略提交自己的目标，账户协调器合并预算和订单，统一检查可用资金、总仓位和证券可卖数量。

券商股票持仓通常按账户和代码汇总，不能仅靠订单的 `strategy_name` 把已有持仓自动分给不同策略。建立策略自己的数量、成本和资金记录，按成交分配；公司行为、转入转出、手工交易出现差异时要有明确的调整规则。

两个策略同时持有同一代码时，还要定义“每个策略最多 N 只”和“账户最多 M 只”的关系，以及策略间相反方向的目标如何处理。初期可以不允许共享标的；需要共享时再实现明确的内部数量分配和账户净订单。

手工下单和撤单必须被观察到。可选择暂停策略等待确认，或按明确规则接管；不能当它们不存在。新的卖出任务也不能反复使用同一份可卖数量。

## 11. 还需要补齐的上线部分

| 部分 | 最低要求 |
|---|---|
| 数据与日历 | 使用真实交易日历，处理节假日、午间休市、开收盘集合竞价；日线因子使用完整且已结束的数据 |
| 避免使用未来信息 | 财务指标按实际披露时间可用；历史候选范围考虑当时已上市、停牌和退市标的，保留当时可知的数据 |
| 复权与公司行为 | 明确因子复权口径；分红、拆分、转股等更新数量、成本、资金，避免被识别成普通成交差异 |
| 本地长期记录 | 目标版本、风险覆盖、冷却期、订单、成交、资金/证券预留、账户差异与人工操作都有记录及备份 |
| 生命周期 | 开盘前检查，盘中事件处理与对账，收盘处理未结束订单，盘后核对费用、净值和次日状态 |
| 故障恢复 | 断线暂停新增指令；重连先对账；异常退出或升级后处理 `SENDING` / `UNKNOWN`，没有确认结果不能重发 |
| 安全边界 | 凭据放私有配置，消息来源认证，网络访问受限；多个调用者都应经过共同的风险入口 |
| 可观测状态 | 显示目标与实际差异、未结束订单年龄、未知指令、最后有效行情、现金/名额预留、失败原因与当前风险开关 |
| 运行验证 | 历史回测、离线异常演练、真实行情下只输出计划、经明确授权的小规模真实执行；实盘与回测使用同一策略和规划器 |

回测成交模型至少覆盖无法成交、部分成交、交易限制、费用和价格偏差。现有回测桥提供执行环境，不能仅凭回测有成交就假设实盘一定有成交。

必要的故障演练包括：重复目标、旧目标晚到、回报先于响应、重复成交、撤单过程中成交、卖出未更新持仓、资金查询失败、过期行情、标的卖不掉、下单后进程崩溃、重启后只剩原始合同号、手工交易和同时启动两个实例。

## 12. 离线运行与模板边界

在仓库根目录运行：

```powershell
python examples/external_rotation_template.py
python -B -m unittest discover -s tests/bigqmt_signal_trader -p test_external_rotation_template.py -v
```

示例用虚构标的演示四种状态：先卖退出标的、等待未结束委托、卖不掉的旧标的保留名额、确认清空后再买新标的。第三种状态可能允许给保留标的补仓，但不会突破名额或使用卖不掉的资金预算。

核心调用：

```python
targets = select_targets(verified_scores, current_symbols, count=N, retain_rank=N + buffer)
signal = TargetPortfolio(account_id, strategy_id, version, created_at,
                         data_cutoff, expires_at, targets)
plan = build_plan(signal, reconciled_account, quotes, instrument_rules, settings, now)
```

模板默认只处理等额、只做多、专用账户组合，不处理信用杠杆、期货/期权、卖空或多币种结算。它依赖已验证的标的规则、来源时间和账户对账结果。非法数字可能抛出 `ValueError`，协调器应记录并暂停规划。

模板采取整批等待，未完成的旧委托会阻止其他新订单；这是有意的保守执行规则。需要并行处理时可扩展为：

```text
预计完成后数量 = 当前真实数量 + 未结束买单剩余量 - 未结束卖单剩余量
待补数量 = 目标数量 - 预计完成后数量
```

但是这条公式只有在真实数量和成交记录已对齐、同一部分成交未被两次扣除时才成立。已发送但尚未查询到的订单、结果未知的指令也必须纳入预留；先把这套记录和对账完成，再扩展并行执行。

再次调用 `build_plan()` 会对相同输入输出相同计划，不会记得上次已经发过订单。避免重复发送的责任在账户锁、长期订单记录和执行协调器，不在这个纯计算函数中。
